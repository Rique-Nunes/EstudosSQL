# **Materialized Views no Oracle Database: Conceitos, Arquitetura e Roteiro Prático no Oracle APEX**

# **1\. Fundamentos Teóricos: O que é uma Materialized View?**

## **Definição**

No Oracle Database, existe uma diferença fundamental entre uma **View Standard (Padrão)** e uma **Materialized View (View Materializada)**:

* **View Padrão**: É um objeto puramente lógico/virtual. Ela não armazena dados em disco; armazena apenas a definição SQL da consulta. Toda vez que uma View padrão é executada, o banco de dados processa internamente a consulta subjacente acessando as tabelas base.  
* **Materialized View**: É um objeto físico que executa a consulta subjacente e **persiste os resultados em disco**, comportando-se como uma tabela com dados pré-computados. Isso elimina a necessidade de reprocessar consultas complexas, junções custosas e agregações pesadas repetidamente.

## **Casos de Uso**

As Materialized Views são amplamente utilizadas em arquiteturas de bancos de dados modernos para otimização de performance:

* **Data Warehouses & Business Intelligence (BI)**: Pré-computação de relatórios analíticos, dashboards e agregações de grande volume.  
* **Agregação de Dados**: Consolidação de milhões de registros transacionais em resumos por hora, dia, categoria ou região.  
* **Computação Distribuída e Replicação**: Leitura local de dados replicados a partir de bancos de dados remotos via Database Links (`DBLINK`), reduzindo a latência de rede.  
* **Otimização de Consultas de Alto Custo**: Aceleração de consultas analíticas pesadas em ambientes OLTP sem sobrecarregar o processamento transacional.

## **Mecanismos de Atualização (Refresh Modes e Methods)**

A sincronização dos dados entre as tabelas base e a Materialized View pode ser configurada combinando **métodos** e **modos temporais**.

| Método | Descrição |
| :---- | :---- |
| `COMPLETE` | Recalcula e substitui a totalidade dos dados da Materialized View executando a consulta original do zero. |
| `FAST` | Aplica atualizações incrementais na Materialized View processando apenas as alterações (DML) ocorridas nas tabelas base desde a última atualização, utilizando o **Materialized View Log (`MLOG$`)**. |
| `FORCE` | Método padrão. O Oracle tenta realizar o `FAST refresh`; caso os pré-requisitos não sejam atendidos, executa automaticamente um `COMPLETE refresh`. |
| `NEVER` | Desativa atualizações automáticas ou manuais da Materialized View. |

| Modo Temporal | Descrição |
| :---- | :---- |
| `ON DEMAND` | A atualização é executada manualmente ou via tarefas agendadas (`Scheduler`) através da procedure `DBMS_MVIEW.REFRESH`. |
| `ON COMMIT` | A atualização é disparada automaticamente de forma transacional no instante exato em que ocorre um `COMMIT` na tabela base. |

## **Query Rewrite**

O **Query Rewrite** é um recurso do otimizador de consultas baseado em custo (*Cost-Based Optimizer \- CBO*) do Oracle. Quando habilitado, o otimizador intercepta consultas executadas diretamente nas **tabelas base** e as redireciona automaticamente para a **Materialized View**, caso perceba que a View possui os dados pré-computados necessários.

Essa reescrita ocorre de forma transparente para as aplicações, sem que a instrução SQL original precise ser alterada no código fonte.

## **Etapa 2: Criação do Materialized View Log (Necessário para Fast Refresh)**

Para permitir que o Oracle realize atualizações incrementais (`FAST Refresh`), é necessário criar um log de alterações na tabela base transacional (`tb_vendas`).

```
CREATE MATERIALIZED VIEW LOG ON tb_vendas
WITH ROWID, SEQUENCE (id_produto, quantidade, valor_total)
INCLUDING NEW VALUES;
```

## **Etapa 3: Criação da Materialized View com Agregação**

Crie a Materialized View consolidando o volume de vendas e o faturamento total por produto.

```
CREATE MATERIALIZED VIEW mv_vendas_por_produto
BUILD IMMEDIATE
REFRESH FAST ON DEMAND
ENABLE QUERY REWRITE
AS
SELECT 
    v.id_produto,
    COUNT(*) AS total_transacoes,
    SUM(v.quantidade) AS qtd_total_vendida,
    SUM(v.valor_total) AS faturamento_total,
    COUNT(v.valor_total) AS count_faturamento
FROM tb_vendas v
GROUP BY v.id_produto;
```

*Nota Didática*: A inclusão das colunas `COUNT(*)` e `COUNT(v.valor_total)` é um requisito arquitetural do Oracle para dar suporte ao `FAST REFRESH` em visões materializadas contendo funções de agregação `SUM`. O banco utiliza esses contadores internamente para ajustar médias e somas quando registros são excluídos ou atualizados na tabela base.

## **Etapa 4: Consulta e Validação Inicial**

Verifique a integração entre os dados materializados pré-computados e as tabelas de domínio.

```
SELECT 
    p.nome_produto,
    p.categoria,
    mv.total_transacoes,
    mv.qtd_total_vendida,
    mv.faturamento_total
FROM mv_vendas_por_produto mv
JOIN tb_produtos p ON p.id_produto = mv.id_produto
ORDER BY mv.faturamento_total DESC;
```

## **Etapa 5: Simulação de Novos Dados e Atualização (Refresh)**

Insira novas transações na tabela base e observe a natureza física da sincronização da Materialized View.

```
-- 1. Inserir nova venda expressiva para o Produto ID 1
INSERT INTO tb_vendas (id_produto, quantidade, data_venda, valor_total)
VALUES (1, 5, SYSDATE, 22500.00);

-- 2. Consultar a MV antes do Refresh
-- (Observe que os valores permanecem inalterados, pois a MV é física)
SELECT * FROM mv_vendas_por_produto WHERE id_produto = 1;

-- 3. Executar o Refresh incremental manual via bloco PL/SQL
BEGIN
    DBMS_MVIEW.REFRESH(
        LIST => 'MV_VENDAS_POR_PRODUTO',
        METHOD => 'F' -- 'F' = Fast Refresh, 'C' = Complete Refresh
    );
END;
/

-- 4. Consultar a MV após o Refresh (Valores devidamente atualizados)
SELECT * FROM mv_vendas_por_produto WHERE id_produto = 1;
```

# **3\. Checklist de Boas Práticas e Considerações de Performance**

* **Estratégia FAST vs. COMPLETE**: Prefira `REFRESH FAST` para tabelas de grande volume com atualizações pontuais frequentes. Utilize `REFRESH COMPLETE` em tabelas pequenas, dimensões ou consultas complexas cujas regras de agregações não preencham os pré-requisitos rígidos do `FAST Refresh`.  
* **Cuidado com o modo ON COMMIT**: Evite utilizar `REFRESH ON COMMIT` em sistemas OLTP de altíssima concorrência. Esse modo faz com que a atualização da Materialized View ocorra dentro da mesma transação do usuário, aumentando o tempo de resposta do `COMMIT` e a ocorrência de contenção por locks.  
* **Indexação da Materialized View**: Como a Materialized View se comporta fisicamente como uma tabela, crie índices secundários (B-Tree ou Bitmap) nas colunas da própria Materialized View utilizadas em cláusulas `WHERE`, `JOIN` e `ORDER BY` de relatórios analíticos.  
* **Manutenção do MLOG\$**: Monitore o crescimento da tabela `MLOG$`. Se uma Materialized View `FAST` ficar sem atualizar por longos períodos, o log continuará acumulando registros de alteração, ocupando espaço excessivo na `TABLESPACE`.
