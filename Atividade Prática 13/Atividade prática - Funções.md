# **Stored Functions no Oracle Database: Conceitos, Arquitetura e Roteiro Prático no Oracle APEX**

Este manual apresenta os fundamentos teóricos, a arquitetura interna e um laboratório prático para o desenvolvimento de **Stored Functions** no Oracle Database, utilizando a interface SQL Commands do **Oracle APEX SQL Workshop**.

# **1\. Fundamentos Teóricos: O que é uma Stored Function?**

## **Definição e Propósito**

Uma **Stored Function** é um bloco PL/SQL nomeado, compilado e armazenado diretamente no catálogo do banco de dados. Sua principal característica estrutural é a obrigatoriedade de retornar **um único valor** (seja ele de tipo escalar ou composto) para o ambiente chamador, por meio da cláusula RETURN.

As funções são projetadas primordialmente para:

* Transformações e manipulações de dados em consultas SQL.  
* Cálculos matemáticos, financeiros e estatísticos reutilizáveis.  
* Implementação de regras de negócio determinísticas.  
* Enriquecimento e padronização de campos em relatórios analíticos.

## **Anatomia de uma Function**

A estrutura basilar de uma Stored Function em PL/SQL é composta pelas seguintes seções:

1. **Cabeçalho**: Define o nome da função, seus parâmetros de entrada/saída (`IN`, `OUT`, `IN OUT`) e o tipo de dado do valor de retorno.  
2. **Seção Declarativa**: Compreendida entre o `IS` (ou `AS`) e o `BEGIN`. Define variáveis locais, constantes, tipos e cursores internos. *Não utiliza a palavra-chave `DECLARE`*.  
3. **Seção Executável**: Iniciada por `BEGIN` e finalizada por `END`. Contém a lógica algorítmica do programa e exige pelo menos uma instrução `RETURN expressao;` alcançável.  
4. **Seção de Tratamento de Exceções**: Opcional, iniciada por `EXCEPTION`. Trata erros em tempo de execução garantindo a integridade da chamada, frequentemente retornando um valor *fallback* ou de contingência.

## **Níveis de Pureza e Restrições de Uso em SQL (Purity Levels)**

Para que uma função PL/SQL possa ser invocada diretamente em expressões SQL (como comandos `SELECT`, cláusulas `WHERE`, `ORDER BY` ou `GROUP BY`), ela precisa seguir regras rígidas de integridade conhecidas historicamente como níveis de pureza:

* **Restrição de DML**: A função não pode executar instruções DML (`INSERT`, `UPDATE`, `DELETE`) nas tabelas afetadas pela consulta principal ou alterar o estado global do banco de dados durante a leitura.  
* **Controle de Transação**: Não deve conter comandos de finalização de transação (`COMMIT`, `ROLLBACK` ou `SAVEPOINT`), exceto quando configurada explicitamente em um contexto isolado através de `PRAGMA AUTONOMOUS_TRANSACTION`.  
* **Sem Alteração de Estado do Pacote**: Não deve alterar variáveis públicas de pacotes (estado do pacote) se executada em consultas remotas ou paralelas.

## **Cláusulas Avançadas de Otimização**

* **`DETERMINISTIC`**: Sinaliza ao otimizador de consultas (*Query Optimizer*) que a função sempre produzirá rigorosamente o mesmo valor de retorno quando fornecida com o mesmo conjunto de parâmetros de entrada. Esta cláusula é pré-requisito indispensável para a criação de **Function-Based Indexes (FBI)** e para a otimização de expressões em visualizações materializadas.  
* **`RESULT_CACHE`**: Instrui o Oracle a armazenar no cache da SGA (*Shared Global Area*) os resultados já computados da função. Caso a função seja invocada novamente com os mesmos argumentos, o motor do Oracle recupera o valor diretamente da memória sem reexecutar o corpo do algoritmo, reduzindo drasticamente o consumo de CPU.

## **Diferenças Essenciais: Function vs Procedure**

| Característica | Stored Function | Stored Procedure |
| :---- | :---- | :---- |
| **Obrigatoriedade de Retorno** | Obrigatório via cláusula `RETURN` no cabeçalho e corpo. | Opcional (não possui tipo de retorno no cabeçalho). |
| **Invocação em SQL** | Pode ser chamada diretamente em instruções `SELECT`, `WHERE`, etc. | Não pode ser chamada em comandos SQL normais. |
| **Propósito Principal** | Computar e retornar valores/expressões. | Executar fluxos de processamento transacional e DML. |
| **Parâmetros** | Predominantemente `IN` (uso de `OUT` deve ser evitado). | Utiliza amplamente parâmetros `IN`, `OUT` e `IN OUT`. |
| **Chamada em PL/SQL** | Utilizada do lado direito de atribuições (`v_val := fnc(...)`). | Invocada como instrução autônoma (`proc(...);`). |

### Etapa 2: Criação de Função Determinística Simples (Cálculo de Desconto Tributário)

A função abaixo calcula o Imposto de Renda Retido na Fonte (IRRF) com base no salário bruto. Como o cálculo depende unicamente do parâmetro de entrada, a diretiva `DETERMINISTIC` é aplicada.

```sql
CREATE OR REPLACE FUNCTION fnc_calcular_irrf (
    p_salario_bruto IN NUMBER
) RETURN NUMBER 
DETERMINISTIC
IS
    v_imposto NUMBER(10,2) := 0;
BEGIN
    IF p_salario_bruto IS NULL OR p_salario_bruto <= 2259.20 THEN
        v_imposto := 0;
    ELSIF p_salario_bruto <= 2826.65 THEN
        v_imposto := (p_salario_bruto * 0.075) - 169.44;
    ELSIF p_salario_bruto <= 3751.05 THEN
        v_imposto := (p_salario_bruto * 0.15) - 381.44;
    ELSIF p_salario_bruto <= 4664.68 THEN
        v_imposto := (p_salario_bruto * 0.225) - 662.77;
    ELSE
        v_imposto := (p_salario_bruto * 0.275) - 896.00;
    END IF;

    RETURN ROUND(GREATEST(v_imposto, 0), 2);
EXCEPTION
    WHEN OTHERS THEN
        RETURN 0;
END fnc_calcular_irrf;
/
````

## **Etapa 3: Criação de Função com Consulta ao Banco (Cálculo de Comissão de Vendas)**

A função `fnc_obter_comissao` realiza uma consulta SQL na tabela de vendas para obter o volume faturado no mês e aplica uma alíquota progressiva.

```
CREATE OR REPLACE FUNCTION fnc_obter_comissao (
    p_id_colaborador IN NUMBER,
    p_mes_ano        IN VARCHAR2
) RETURN NUMBER IS
    v_total_vendas NUMBER(12,2) := 0;
    v_percentual   NUMBER(5,4) := 0;
BEGIN
    -- Obter o volume de vendas do colaborador no mês de referência
    SELECT NVL(SUM(total_vendido), 0)
    INTO v_total_vendas
    FROM tb_vendas_colaborador
    WHERE id_colaborador = p_id_colaborador
      AND mes_ano = p_mes_ano;

    -- Escala de comissionamento progressivo
    IF v_total_vendas >= 100000.00 THEN
        v_percentual := 0.05; -- 5%
    ELSIF v_total_vendas >= 50000.00 THEN
        v_percentual := 0.035; -- 3.5%
    ELSIF v_total_vendas > 0 THEN
        v_percentual := 0.02; -- 2%
    ELSE
        v_percentual := 0;
    END IF;

    RETURN ROUND(v_total_vendas * v_percentual, 2);
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        RETURN 0;
    WHEN OTHERS THEN
        RETURN 0;
END fnc_obter_comissao;
/
```

## **Etapa 4: Integração de Funções em Consultas SQL e Relatórios Analíticos**

Demonstração do uso das funções criadas diretamente nas projeções e filtros de relatórios SQL.

```
-- 1. Relatório consolidado de remuneração bruta, comissão e desconto de IRRF
SELECT 
    c.id_colaborador,
    c.nome,
    c.departamento,
    c.salario_base,
    fnc_obter_comissao(c.id_colaborador, '10/2026') AS comissao_outubro,
    (c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) AS remuneracao_bruta,
    fnc_calcular_irrf(c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) AS desconto_irrf,
    (c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) - 
    fnc_calcular_irrf(c.salario_base + fnc_obter_comissao(c.id_colaborador, '10/2026')) AS salario_liquido_estimado
FROM tb_colaboradores c
ORDER BY remuneracao_bruta DESC;

-- 2. Uso da função dentro da cláusula WHERE para filtragem de faixa
SELECT nome, salario_base
FROM tb_colaboradores
WHERE fnc_calcular_irrf(salario_base) > 300.00;
```

# **4\. Checklist de Boas Práticas e Arquitetura**

* **Garantia de Retorno**: Certifique-se de que todos os caminhos lógicos do código (incluindo todas as ramificações `IF/ELSE` e blocos `EXCEPTION`) possuam uma instrução `RETURN`.  
* **Prevenção do Problema N+1**: Evite executar instruções `SELECT` dentro de funções que serão invocadas repetidamente sobre grandes volumes de dados em consultas SQL.  
* **Uso Adequado de Determinismo**: Declare a instrução `DETERMINISTIC` apenas em funções puras, onde o retorno depende exclusivamente dos parâmetros passados, sem consultas a tabelas dinâmicas ou datas do sistema (`SYSDATE`).  
* **Encapsulamento em Pacotes**: Em ambientes de produção, evite criar funções standalone. Agrupe funções correlatas dentro de **Packages** (`CREATE PACKAGE`) para otimizar o carregamento em memória e melhorar a organização do código.
