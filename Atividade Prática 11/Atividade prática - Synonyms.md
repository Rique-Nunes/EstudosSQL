# **Synonyms no Oracle Database: Conceitos, Arquitetura e Roteiro Prático no Oracle APEX**

# **1\. Fundamentos Teóricos: O que é um Synonym?**

## **Definição e Propósito**

Um **synonym** (sinônimo) é um *alias* ou apelido alternativo para qualquer objeto pertencente a um schema do banco de dados Oracle — incluindo tabelas, views, materialized views, sequences, procedimentos (procedures), funções (functions), pacotes (packages), tipos definidos pelo usuário (user-defined types) ou até mesmo outros sinônimos.

É fundamental compreender que um sinônimo **não armazena dados físicos** nem definições de estrutura física. Ele atua puramente como um apontador ou entrada lógica registrada no **dicionário de dados** do Oracle Database.

## **Vantagens Arquiteturais**

* **Transparência de Localização e Schema**: Permite que as aplicações e os desenvolvedores acessem objetos sem a necessidade de prefixar o nome do schema proprietário original (por exemplo, executar `SELECT * FROM clientes` em vez de `SELECT * FROM erp_financeiro.tb_clientes_faturamento_v2`).  
* **Isolamento e Segurança Indireta**: Oculta o nome físico real das tabelas, o esquema de nomenclatura interno e o proprietário original dos dados, reduzindo a exposição da estrutura interna do banco para ferramentas externas ou usuários finais.  
* **Facilidade em Manutenção e Refatoração**: Em cenários de refatoração de banco de dados — onde uma tabela base é renomeada, particionada, substituída por uma view complexa ou movida para outro schema —, basta atualizar o apontamento do sinônimo. Nenhuma instrução SQL incorporada na camada de aplicação precisa ser modificada.  
* **Abstração de Objetos Remotos (Database Links)**: Simplifica drasticamente o consumo de objetos situados em instâncias remotas via DBLINK (exemplo: utilizar `SELECT * FROM produtos` em substituição a `SELECT * FROM tb_produtos@db_link_matriz`).

## **Classificação de Synonyms**

| Tipo | Pertencimento | Escopo de Visibilidade | Permissão para Criação |
| :---- | :---- | :---- | :---- |
| **Private Synonym** | Schema específico do usuário criador. | Acessível apenas pelo proprietário do schema (ou usuários com privilégios concedidos). | Privilégio de sistema `CREATE SYNONYM`. |
| **Public Synonym** | Schema especial de sistema denominado `PUBLIC`. | Acessível por todos os usuários do banco de dados. | Privilégio de sistema `CREATE PUBLIC SYNONYM`. |

## **Ordem de Resolução de Nomes no Oracle Database**

Quando uma instrução SQL referencia um objeto não qualificado diretamente (por exemplo, `SELECT * FROM funcionarios`), o mecanismo de parsing do Oracle resolve o nome seguindo rigorosamente a seguinte hierarquia de prioridade:

1. **Objeto Local do Schema**: Tabela, view, sequence ou outro objeto pertencente diretamente ao próprio schema do usuário conectado.  
2. **Sinônimo Privado**: Sinônimo privado pertencente ao schema do usuário conectado.  
3. **Sinônimo Público**: Sinônimo público criado no schema `PUBLIC` do banco de dados.  
4. **Erro de Resolução**: Se o objeto não for localizado em nenhum dos níveis acima, o Oracle interrompe a execução e retorna a exceção `ORA-00942: table or view does not exist`.

## **Distinção Fundamental: Synonym vs. Privilégio**

Um sinônimo é estritamente uma conveniência de endereçamento e **NÃO concede privilégios de acesso**. A existência de um sinônimo não ignora o modelo de segurança do Oracle: o usuário que tenta acessar um objeto via sinônimo ainda deve possuir explicitamente os privilégios de objeto necessários (`SELECT`, `INSERT`, `UPDATE`, `EXECUTE`, etc.) concedidos pelo proprietário do objeto base ou concedidos à *ROLE* do usuário.

# **2\. Roteiro Prático: Laboratório no Oracle APEX (SQL Workshop)**

**Ambiente de Execução**: Oracle Application Express (APEX) \$\\rightarrow\$ SQL Workshop \$\\rightarrow\$ SQL Commands.

## **Etapa 1: Criação da Tabela com Nomenclatura Técnica Complexa**

Nesta etapa, criaremos uma tabela simulando um ambiente corporativo legado, onde os nomes dos objetos tendem a ser extensos e padronizados com prefixos rigorosos.

```
-- 1. Criação da tabela base com nome corporativo complexo
CREATE TABLE tb_cad_clientes_corp_nacional (
    id_cliente      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    codigo_empresa  VARCHAR2(15) NOT NULL,
    razao_social    VARCHAR2(100) NOT NULL,
    cidade          VARCHAR2(50) NOT NULL,
    limite_credito  NUMBER(12,2) NOT NULL,
    status_conta    VARCHAR2(15) DEFAULT 'ATIVO' NOT NULL
);

-- 2. Carga inicial de dados representativa
INSERT INTO tb_cad_clientes_corp_nacional (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-001', 'Logística Integrada Sudeste SA', 'Rio de Janeiro', 250000.00, 'ATIVO');

INSERT INTO tb_cad_clientes_corp_nacional (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-002', 'Rede Varejista do Brasil Ltda', 'São Paulo', 500000.00, 'ATIVO');

INSERT INTO tb_cad_clientes_corp_nacional (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-003', 'Metalúrgica Vale do Paraíba', 'Belo Horizonte', 180000.00, 'INATIVO');

COMMIT;
```

## **Etapa 2: Criação do Sinônimo Privado (Abstração Semântica)**

Criaremos um sinônimo privado amigável para simplificar a escrita das consultas e desacoplar o código da aplicação do nome físico da tabela.

```
-- 1. Criar o Synonym privado apontando para a tabela complexa
CREATE OR REPLACE SYNONYM clientes 
FOR tb_cad_clientes_corp_nacional;

-- 2. Consultar os dados através do Synonym recém-criado
SELECT id_cliente, codigo_empresa, razao_social, cidade, limite_credito
FROM clientes
WHERE status_conta = 'ATIVO';
```

*Nota Didática*: Observe como a consulta torna-se extremamente legível e concisa, omitindo completamente a complexidade da nomenclatura física original do objeto no banco de dados.

## **Etapa 3: Operações DML Transparentes através de Sinônimos**

Sinônimos funcionam transparentemente como alvos para comandos de manipulação de dados (DML). Qualquer alteração via sinônimo afeta diretamente a tabela base.

```
-- 1. Inserir um novo registro utilizando o Synonym
INSERT INTO clientes (codigo_empresa, razao_social, cidade, limite_credito, status_conta)
VALUES ('CORP-004', 'Distribuidora Farmacêutica Rio', 'Niterói', 320000.00, 'ATIVO');
COMMIT;

-- 2. Atualizar o limite de crédito através do Synonym
UPDATE clientes
SET limite_credito = limite_credito * 1.10
WHERE codigo_empresa = 'CORP-004';
COMMIT;

-- 3. Validar consultando tanto o Synonym quanto a tabela física de origem
SELECT codigo_empresa, razao_social, limite_credito 
FROM clientes 
WHERE codigo_empresa = 'CORP-004';

SELECT codigo_empresa, razao_social, limite_credito 
FROM tb_cad_clientes_corp_nacional 
WHERE codigo_empresa = 'CORP-004';
```

## **Etapa 4: Abstração de Sequences com Sinônimos**

Os sinônimos também se aplicam a geradores de sequências numéricas (*sequences*), permitindo padronizar e ocultar a implementação subjacente de chaves primárias.

```
-- 1. Criação de uma Sequence com nome técnico
CREATE SEQUENCE seq_tb_cad_clientes_corp_id
    START WITH 500
    INCREMENT BY 1
    NOCACHE;

-- 2. Criação de um Synonym para a Sequence
CREATE OR REPLACE SYNONYM seq_clientes 
FOR seq_tb_cad_clientes_corp_id;

-- 3. Consumir valores utilizando o Synonym
SELECT seq_clientes.NEXTVAL AS proximo_id FROM DUAL;
SELECT seq_clientes.CURRVAL AS id_atual FROM DUAL;
```

## **Etapa 5: O Poder da Refatoração Transparente (Substituição por View)**

Demonstração do ciclo de vida e manutenção: alteraremos a regra de negócio redirecionando o sinônimo para uma view filtrada, sem que as consultas da aplicação precisem sofrer alterações.

```
-- 1. Criar uma View que expõe apenas clientes ativos com regras de negócio
CREATE OR REPLACE VIEW vw_clientes_ativos AS
SELECT id_cliente, codigo_empresa, razao_social, cidade, limite_credito
FROM tb_cad_clientes_corp_nacional
WHERE status_conta = 'ATIVO';

-- 2. Redirecionar o Synonym existente para a View (sem parar a aplicação)
CREATE OR REPLACE SYNONYM clientes 
FOR vw_clientes_ativos;

-- 3. Executar exatamente a mesma consulta que a aplicação sempre executou
SELECT * FROM clientes;
```

*Nota Didática*: Nenhuma linha de código SQL na camada de aplicação precisa ser alterada. O apontamento foi alterado em tempo de execução no dicionário de dados, fazendo com que o sinônimo agora forneça os dados já filtrados pela view.

## **Etapa 6: Consulta e Auditoria no Dicionário de Dados**

Auditar as definições de sinônimos pertencentes ao schema do usuário atual por meio da view de dicionário de dados `USER_SYNONYMS`.

```
-- 1. Listar todos os sinônimos do usuário e seus alvos reais
SELECT synonym_name, table_owner, table_name, db_link
FROM user_synonyms
ORDER BY synonym_name;
```

# **3\. Exercícios Práticos de Fixação**

## **Exercício 1: Simulação de Ambiente Multi-Schema e Privilégios**

**Cenário**: Explique e elabore o fluxo completo de comandos SQL e DCL necessários para que o usuário `ANALISTA_BI` consiga consultar a tabela `EMPLOYEES` pertencente ao schema `HR`, utilizando simplesmente a instrução `SELECT * FROM func;`.

**Resolução Esperada**:

1. O proprietário `HR` (ou administrador) concede privilégio de leitura na tabela para `ANALISTA_BI`:

```
GRANT SELECT ON hr.employees TO analista_bi;
```

2. No schema do usuário `ANALISTA_BI`, cria-se o sinônimo privado apontando para o objeto do schema `HR`:

```
CREATE SYNONYM func FOR hr.employees;
```

3. O usuário `ANALISTA_BI` pode então executar:

```
SELECT * FROM func;
```

## **Exercício 2: Ordem de Resolução de Nomes**

**Cenário**: Considere que o usuário conectado possui em seu ambiente:

1. Uma tabela física própria chamada `PEDIDOS`.  
2. Um sinônimo privado chamado `PEDIDOS` (apontando para `FATURAMENTO.TB_PEDIDOS`).  
3. Um sinônimo público chamado `PEDIDOS` (apontando para `GLOBAL.TB_PEDIDOS`).

Ao executar a consulta `SELECT * FROM pedidos;`, qual objeto será retornado pelo Oracle Database? Justifique com base nas regras de parsing.

**Resolução Esperada**:  
Será consultada a **tabela física própria** pertencente ao schema do usuário. De acordo com a árvore de resolução de nomes do Oracle, objetos locais do próprio schema possuem prioridade 1 (máxima), sendo avaliados antes de sinônimos privados (prioridade 2\) e sinônimos públicos (prioridade 3).

## **Exercício 3: Sinônimos Inválidos / Órfãos**

Cenário: O que acontece com um sinônimo se o objeto subjacente para o qual ele aponta (ex: tabela base) for excluído com a instrução DROP TABLE? O sinônimo é removido automaticamente? O que ocorre ao tentar consultá-lo?

**Resolução Esperada**:  
O sinônimo **não é excluído automaticamente**. Ele permanece cadastrado no dicionário de dados, porém passa a ser um sinônimo órfão (inválido). Ao tentar executar uma instrução SQL contra este sinônimo, o Oracle tentará resolver o apontamento, não encontrará o objeto base e retornará a exceção `ORA-00942: table or view does not exist`.

# **4\. Checklist de Boas Práticas e Governança de Banco de Dados**

* **Uso Criterioso de Sinônimos Públicos**: Evite a criação desmedida de *Public Synonyms*. Por estarem situados no namespace global (`PUBLIC`), podem causar conflitos de nomes não intencionais, ambiguidades na resolução de consultas e potenciais brechas de segurança.  
* **Comportamento em DDL**: Lembre-se de que a remoção de um sinônimo por meio da instrução `DROP SYNONYM` elimina apenas a entrada do apontador no dicionário de dados, mantendo o objeto base (tabela, view, sequence) intacto.  
* **Validação de Objetos Órfãos**: Mantenha rotinas de manutenção preventivas executando scripts de auditoria que cruzem a `USER_SYNONYMS` ou `ALL_SYNONYMS` com a `ALL_OBJECTS`, garantindo a identificação e remoção de sinônimos cujos objetos de destino foram eliminados.
